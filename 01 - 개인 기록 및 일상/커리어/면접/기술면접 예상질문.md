### 1. 운영체제

**프로세스와 스레드의 차이**

> "프로세스는 운영체제로부터 독립된 메모리 공간을 할당받아 실행되는 프로그램 단위이고, 스레드는 프로세스 안에서 동작하는 작업 단위로 스택을 제외한 메모리(코드/데이터/힙)를 다른 스레드와 공유합니다. 그래서 스레드는 생성 비용이 더 싸고 컨텍스트 스위칭도 빠릅니다."
> 

**뮤텍스와 세마포어의 차이**

> "둘 다 임계구역을 보호해서 동시 접근으로 데이터가 깨지는 걸 막는 동기화 도구입니다. 뮤텍스는 한 스레드만 접근할 수 있고 락을 건 스레드만 풀 수 있습니다. 세마포어는 접근 허용 개수를 지정할 수 있고, 락을 건 스레드가 아니어도 해제할 수 있어서 커넥션 풀처럼 동시에 여러 스레드가 쓸 수 있는 자원을 제어할 때 씁니다."
다만, 자바 단의 Lock 이나 Semaphore는 단일 서버(하나의 JVM)안에서만 유효합니다. 실제 운영 환경에서는 다중 서버를 띄우기 때문에 이런 스레드 동기화 문제를 해결하기 위해 코드레벨의 제어보다는 데이터베이스의 비관적/낙관적 락을 사용하거나, Redis를 활용한 분산학 구조를 적용하여 해결하는 것이 더 안전하고 실무적인 접근이라고 생각합니다.
> 

**프로세스 간 통신(IPC) 방법**

> "소켓, 파이프, 공유 메모리, 메시지 큐 같은 방식이 있다고 알고 있습니다. 실무에서는 REST API나 웹소켓 같은 네트워크 기반 통신 위주로 다뤄봤고, OS 레벨의 파이프나 공유 메모리를 직접 써본 경험은 없습니다." *(모르는 부분은 이렇게 솔직히 구분해서 답하는 게 안전합니다)*
>

### 2. 캐시 전략

**DB 부하가 많을 때 캐시를 어떻게 쓰겠나요 / Redis를 프로젝트에서 어떻게 활용하셨나요**

> "조회 부하에는 Cache-Aside를, 쓰기 부하에는 Write-Back 같은 일반적인 캐시 전략을 쓸 수 있습니다. 저는 전기차 충전 플랫폼을 개발할 때 Redis를 '비동기 요청-응답의 상태 관리소'로 활용해서 불필요한 DB 트랜잭션을 줄인 경험이 있습니다.
> 
> 
> 저희 플랫폼은 충전기와 비동기로 통신하는 구조였습니다. 서버가 충전기에 제어 요청을 보내면 즉시 처리되는 게 아니라 나중에 응답이 돌아오는데, 이 '요청 대기 상태'를 매번 RDBMS에 저장하면 불필요한 쓰기 부하가 발생합니다. 그래서 요청을 보낼 때 해당 작업의 컨텍스트(요청 정보)를 처리 속도가 빠른 Redis에 임시로 저장해뒀다가, 충전기로부터 응답이 오면 Redis에서 컨텍스트를 꺼내와 비즈니스 로직을 처리하고, 최종적으로 완료된 결과만 DB에 저장하도록 설계했습니다.
> 
> 이 방식으로 아직 완료되지 않은 중간 상태를 DB에 기록하는 비용을 없앴고, 충전기 네트워크 문제로 응답이 오지 않는 경우를 대비해 Redis에 짧은 TTL을 설정해서 타임아웃 시 데이터가 자동으로 소멸되도록 메모리 누수까지 방지했습니다."
> 
> 후속으로 "왜 굳이 Redis였나요, DB로도 되지 않나요?"를 물으면 "매번 생겼다 사라지는 임시 상태를 굳이 RDBMS에 쓰기/삭제할 필요가 없었고, Redis는 인메모리라 훨씬 빠르고 TTL 자동 만료 기능을 기본으로 제공해서 별도 정리 로직 없이도 만료 처리가 됐기 때문"이라고 답하면 자연스럽게 이어집니다.
>

### 4. DB 부하 / 수평 확장

**DB에 부하가 많이 걸렸을 때 어떻게 해결하시겠어요**

> "먼저 슬로우 쿼리를 찾아 인덱스를 추가하거나 쿼리를 개선합니다. 그다음 Redis 같은 캐시로 반복 조회 부하를 줄이고, 읽기 부하가 크면 read replica로 읽기/쓰기를 분리합니다. 그래도 부족하면 파티셔닝이나 샤딩으로 수평 확장을 검토합니다."
> 

**DB를 수평적으로 확장하는 방법**

> "읽기는 read replica를 추가하고, 쓰기까지 확장하려면 샤딩으로 여러 DB에 데이터를 분산합니다. 테이블이 크면 수평 파티셔닝으로 로우를 나눠 인덱스 크기를 줄이고 조회·insert 성능을 개선할 수 있는데, 여러 샤드·파티션에 걸친 조회나 조인은 성능이 떨어지고 관리가 어려워지는 단점이 있습니다."
> 
> 
> 대규모 트래픽에서 직접 샤딩/파티셔닝을 설계해본 경험이 없다면, 개념 설명 뒤에 "직접 이 정도 규모의 확장을 설계해본 경험은 아직 없습니다"라고 붙이는 게 안전합니다.
>

### 5. Network

**Connection Pool이 무엇인가요**

> "DB 연결을 요청마다 새로 만들고 없애는 건 비용이 크기 때문에, 미리 연결을 만들어 풀에 담아두고 필요할 때 가져다 쓰는 방식입니다. 연결 생성·해제 비용을 줄이고 동시 커넥션 수도 제어할 수 있습니다."
> 

**Socket timeout과 Connection timeout의 차이**

> "Connection timeout은 서버와 연결을 맺기까지 기다리는 최대 시간이고, Socket timeout은 연결된 이후 데이터를 주고받는 도중 응답이 설정 시간보다 늦게 오면 발생하는 타임아웃입니다."
>

### 6. ES(Elasticsearch) / Kafka — 스택 밖 기술

이 두 개는 실무에서 안 써보셨을 가능성이 높은 영역입니다. 억지로 아는 척하기보다, 개념만 짧게 답하고 "직접 다뤄본 경험은 없다"고 명확히 하는 게 훨씬 신뢰를 줍니다.

**Kafka에서 순서를 유지하는 방법**

> "Kafka는 파티션 단위로만 순서를 보장한다고 알고 있습니다. 그래서 순서가 중요한 메시지는 같은 키를 써서 같은 파티션으로 보내야 합니다. 다만 직접 Kafka를 운영해본 경험은 없습니다."
> 

**ES Reindex가 무엇인가요**

> "매핑 정보를 바꿔야 할 때(필드 타입 변경 등) 새 인덱스를 만들어 데이터를 옮기는 작업으로 알고 있고, alias를 활용하면 무중단으로 인덱스를 교체할 수 있다고 들었습니다. 다만 직접 운영해본 경험은 없습니다."
> 

면접에서 이 영역 질문이 나오면, 아는 데까지 짧게 답하고 바로 본인이 실제 강점을 가진 영역(웹소켓 실시간 처리, Redis, 멀티모듈 아키텍처)으로 자연스럽게 연결하는 것도 방법입니다: "이 부분은 실무 경험이 없지만, 비슷하게 실시간 데이터를 다뤘던 [OCPP 웹소켓/Redis 연동] 경험은 있습니다" 식으로요.

### 7. Java 심화

**GC(Garbage Collection) 종류**

> "힙 메모리에서 참조가 끊긴 객체를 자동으로 회수하는 역할입니다. 힙은 Young(Eden, Survivor)과 Old로 나뉘고, Eden이 차면 Minor GC, Old가 차면 Major GC가 일어납니다. Serial, Parallel, CMS, G1GC가 있고, 최근에는 Stop-The-World 시간을 최소화하는 ZGC도 있다고 알고 있습니다."
> 

**HashMap vs Hashtable vs ConcurrentHashMap**

> "HashMap은 동기화가 안 돼 있어 빠르고 null도 허용합니다. Hashtable은 synchronized로 동기화돼 있어 스레드 세이프하지만 느립니다. 멀티스레드 환경에서는 Hashtable 대신 ConcurrentHashMap을 씁니다. ConcurrentHashMap은 전체에 락을 거는 게 아니라 버킷 단위로 락을 걸어서 성능이 더 좋습니다."
> 

**Stack과 Heap의 차이**

> "Stack은 메서드 호출 시 매개변수, 지역 변수, 호출 정보를 저장하고 스레드마다 독립적으로 가집니다. Heap은 객체와 배열이 저장되는 영역으로 모든 스레드가 공유하고 GC의 대상이 됩니다."
> 

**OutOfMemory가 발생하면 어떻게 대처하나요**

> "힙 덤프를 떠서 어떤 객체가 메모리를 많이 차지하는지 분석합니다. `jmap -dump` 명령으로 덤프를 뜰 수 있고, MAT 같은 툴로 분석해서 메모리 누수면 코드를 수정하고, 실제로 데이터량이 많아서 부족한 거면 힙 크기를 조정합니다."
> 
> - [ ]  실제로 OOM을 직접 겪고 해결해본 경험이 있다면 STAR로 바꿔서 준비해두면 훨씬 강한 답변이 됩니다.

### 8. Spring 심화

**DI(의존성 주입) 방법과 생성자 주입을 선호하는 이유**

> "필드 주입, 세터 주입, 생성자 주입이 있는데 저는 생성자 주입을 선호합니다. 생성자 주입은 객체 생성 시점에 필요한 의존성이 모두 주입되기 때문에 필드를 final로 선언할 수 있어 불변성이 보장되고, 필수 의존성이 누락되면 컴파일 시점에 바로 알 수 있어서 NPE 가능성도 줄어듭니다. 필드 주입은 테스트할 때 의존성을 주입하기 어렵다는 단점이 있어 지양하는 편입니다."
> 

**필터와 인터셉터의 차이**

> "필터는 DispatcherServlet 이전에 서블릿 컨테이너 레벨에서 동작해서 전역적인 로깅이나 인코딩 처리에 적합하고, 인터셉터는 DispatcherServlet 이후 스프링 컨텍스트 안에서 동작해서 핸들러(컨트롤러) 정보까지 알 수 있어 세부적인 인가 처리에 적합합니다."
> 

**DispatcherServlet에서 사용하는 디자인 패턴**

> "프론트 컨트롤러 패턴입니다. 모든 요청을 DispatcherServlet 하나가 먼저 받아서 적절한 컨트롤러로 위임하는 구조입니다." *(카카오 면접복기에서 이 질문에 "템플릿 메서드 아닐까요"라고 추측했다가 틀렸다고 나와 있으니, 정확히 프론트 컨트롤러 패턴으로 기억해두세요.)*

### 9. 디자인 패턴 (기존 정리)

**알고 있는 디자인 패턴을 설명해보세요**

> "싱글톤 패턴은 인스턴스를 하나만 생성해 공유하는 패턴이고 Spring Bean이 기본적으로 이 방식으로 관리됩니다. 전략 패턴은 알고리즘을 인터페이스로 분리해서 런타임에 구현체를 바꿔 끼울 수 있게 하는 패턴이고, 프록시 패턴은 실제 객체 앞단에서 접근을 제어하거나 부가 기능을 추가하는 패턴인데 Spring AOP가 이 방식으로 동작합니다."
> 

**Spring에서 실제로 쓰이는 디자인 패턴**

> • 싱글톤: Bean의 기본 스코프
• 프록시: AOP (트랜잭션, 로깅 등 공통 관심사 처리)
• 템플릿 메서드: JdbcTemplate, RestTemplate
• 팩토리: BeanFactory/ApplicationContext
• 옵저버: ApplicationEventPublisher/EventListener
• 프론트 컨트롤러: DispatcherServlet
> 

**프로젝트에서 디자인 패턴을 의도적으로 적용해본 경험**

> "OCPP는 메시지 타입이 다양하고 타입마다 처리 로직이 다른데, 이걸 하나의 클래스에서 if-else나 switch로 분기하면 타입이 늘어날 때마다 그 클래스를 계속 수정해야 하는 구조가 됩니다. 그래서 메시지 타입별 처리 로직을 공통 인터페이스로 추상화하고, 각 타입에 대응하는 구현체를 별도 클래스로 분리했습니다. 메시지가 들어오면 타입명을 기준으로 리플렉션을 이용해 클래스명이 일치하는 구현체를 동적으로 찾아 실행하는 방식으로 처리했고, 호출하는 쪽은 인터페이스에만 의존하기 때문에 느슨한 결합을 유지할 수 있었습니다."
> 
> 
> 패턴 이름을 물으면 "전략 패턴에 리플렉션 기반 동적 탐색을 결합한 구조"라고 답하고, 설계 원칙을 물으면 개방-폐쇄 원칙(OCP)이라고 답하면 됩니다. "리플렉션 성능 이슈는요?"라고 물으면 "캐싱을 안 해두면 매 요청마다 비용이 발생하지만, 초기화 시점에 타입-클래스 매핑을 캐싱해서 개선할 수 있다"고 답하세요.
> 

**전략 패턴과 템플릿 메서드 패턴의 차이**

> "전략 패턴은 알고리즘 전체를 인터페이스로 분리해서 조합으로 갈아끼우는 방식이고, 템플릿 메서드는 상속으로 전체 흐름은 고정해두고 일부 단계만 재정의하는 방식입니다."
> 

**옵저버 패턴을 실무에서 쓴다면**

> "예약이 취소됐을 때 알림 발송, 통계 업데이트, 로그 적재를 동시에 처리해야 한다면, 순차 호출 대신 이벤트를 발행하고 각 리스너가 구독해서 처리하는 방식으로 분리할 수 있습니다."

### 10. 트랜잭션 / JVM 기본 (기존 정리)

**JVM 메모리 구조**

> "모든 스레드가 공유하는 Method Area(클래스/메서드 정보)와 Heap(객체/배열), 스레드마다 독립적으로 가지는 Stack, PC Register, Native Method Stack으로 구성됩니다."
> 

**트랜잭션 전파(propagation) 옵션 차이**

> "REQUIRED는 기존 트랜잭션이 있으면 참여하고 없으면 새로 만들고, REQUIRES_NEW는 무조건 새 트랜잭션을 독립적으로 시작합니다. 메인 로직은 실패해도 로그는 반드시 남겨야 한다면 로그 저장 부분만 REQUIRES_NEW로 분리하는 식으로 씁니다."
> 

**equals()와 hashCode()를 같이 오버라이드해야 하는 이유**

> "HashMap, HashSet은 hashCode로 버킷을 찾고 equals로 실제 동일 객체인지 비교합니다. equals만 오버라이드하면 논리적으로 같은 객체가 다른 버킷에 들어가서 컬렉션에서 못 찾는 문제가 생깁니다."
> 

**JPA N+1 문제와 해결법** *(JPA를 실제로 썼을 경우에만 사용)*

> "지연 로딩 상태에서 리스트를 조회하고 각 엔티티의 연관 데이터를 순회 조회하면 조회 1번 + 건수만큼 추가 조회가 발생하는 문제입니다. fetch join이나 @EntityGraph, batch size 설정으로 해결합니다."
> 

**인덱스는 왜 필요하고 언제 성능을 떨어뜨리나요**

> "인덱스는 조회 성능을 위해 데이터를 정렬된 구조로 별도 저장해서 빠르게 찾게 해주는데, INSERT/UPDATE/DELETE 시마다 같이 갱신해야 해서 쓰기 성능은 떨어집니다. 조회가 훨씬 많은 컬럼 위주로 걸고, 카디널리티가 낮은 컬럼에는 잘 안 겁니다."
> 

**낙관적 락 vs 비관적 락**

> [ ] 실제 동시성 제어 경험(예: 예약/취소 공통 모듈에서 동시 예약 방지)이 있다면 그 사례로 답하세요.

### 16. 성능/부하 테스트 관련

카카오 면접복기에는 4500 TPS 목표로 진행한 성능 테스트 트러블슈팅 사례(서버 증설 → Redis 풀 사이즈 → R2DBC 커넥션 점유 문제 발견 → 쿼리 조인으로 해결)가 자세히 나와 있는데, 이건 그 지원자의 실제 경험이라 그대로 가져다 쓸 내용은 아닙니다. 다만 질문 패턴 자체("TPS 목표 잡고 병목을 하나씩 찾아나간 경험 있나요")는 나올 수 있으니, 대비 방향만 정리해둡니다.

> [ ] 정식으로 TPS를 목표로 잡고 부하 테스트를 진행해본 경험이 없다면, 억지로 지어내지 말고 이렇게 답하는 게 안전합니다: "정식으로 목표 TPS를 잡고 부하 테스트를 진행해본 경험은 아직 없습니다. 다만 실시간 웹소켓 서버를 개발할 때 동시 접속이 몰리는 상황을 고려해서 [세션 관리/커넥션 풀 설정] 방식으로 대비했던 경험은 있습니다." 이후 원리(CPU 코어 수와 풀 사이즈의 관계, 병목은 소거법이나 스레드 덤프로 찾는다는 정도)는 개념으로 알고 있다고 짧게 덧붙이면 됩니다.
