**Q. 지금 다니시는 회사(아와소프트)는 왜 옮기려고 하시나요?**

>

**Q. SI 성격 프로젝트와 자사 서비스 프로젝트를 다 해보셨는데, 어떤 방식이 더 잘 맞으세요?**

> 이력서 안전톡 v2 프로젝트처럼 처음부터 구조를 설계하고 끝까지 책임지고 가져가는 방식이 더 잘 맞았습니다. 통합 플랫폼처럼 고객 요구사항에 맞춰 계속 조율하는 경험도 해봤지만, 제가 구조를 결정하고 그 결과에 대해 책임질 수 있는 자사 서비스 개발 쪽에서 더 몰입이 잘 됐습니다. 팀 규모가 작은 조직에서는 한 사람이 설계부터 배포까지 넓게 관여하게 되는데, 안전톡 프로젝트에서 이미 그런 방식으로 일해본 경험이 있어서 적응이 어렵지 않을 거라고 생각합니다.
> 

**Q. 작은 조직(33명)에서 일하는 것에 대한 부담은 없으신가요?**

> 오히려 익숙한 편입니다. 안전톡 프로젝트도 초기엔 소수 인원으로 시작해서 1인 개발 구간을 거쳤고, 멀티모듈 구조 설계부터 Docker/Jenkins 배포 파이프라인 구축까지 제가 직접 처리해야 했습니다. 담당자가 빠진 프로젝트를 이어받아 마무리한 경험도 있어서, 역할이 넓고 스스로 판단해야 하는 환경에 대한 거부감은 없습니다.

### Part 2. 프로젝트 경험 — 모빌리티 도메인 연계

#### 2-1. 전기차 충전 플랫폼 (가장 직접적으로 연결되는 경험)

**Q. 전기차 충전 플랫폼에서 맡으신 역할을 설명해주세요.**

> 관리자 웹과 사용자 앱의 API 개발, 그리고 충전기와 통신하는 웹소켓 서버 개발을 맡았습니다. 사용자 앱 쪽에서는 소셜 로그인(OAuth), 홈 화면, 설정, 게시판 같은 기본 기능을, 관리자 웹 쪽에서는 공통 코드, 충전소/충전기 모델, 배너, SMS 관리 기능을 개발했습니다. 그리고 OCPP 2.0.1 프로토콜 기반으로 충전기와 실시간 통신하는 신규 웹소켓 서버를 개발해서 충전 세션과 트랜잭션을 관리했습니다.
> 

**Q. OCPP가 뭔가요? 왜 이 프로토콜을 써야 했나요?**

> OCPP(Open Charge Point Protocol)는 전기차 충전기와 충전 관제 시스템(CSMS) 사이의 통신을 표준화한 개방형 프로토콜입니다. 충전기 제조사가 달라도 동일한 방식으로 상태를 주고받을 수 있게 하는 게 목적이고, 웹소켓 위에서 JSON 형태의 메시지를 주고받는 구조입니다. 저희는 충전기와의 통신을 표준을 따르지 않고 자체 규격으로 만들면 제조사가 바뀔 때마다 프로토콜을 새로 맞춰야 하는 문제가 있어서, 업계 표준인 OCPP를 따랐습니다.
> 

**Q. 충전기와의 통신에 왜 REST API가 아니라 웹소켓을 쓰셨나요?**

> 충전기는 충전 시작·정지·상태 변화 같은 이벤트를 서버가 요청하지 않아도 실시간으로 알려야 하고, 반대로 서버도 원격으로 충전 중단 같은 명령을 즉시 내려야 합니다. REST는 클라이언트가 요청해야만 응답이 오는 단방향 구조라 이런 양방향 실시간 통신에는 맞지 않고, 매번 폴링을 하면 지연도 생기고 서버 부하도 커집니다. 웹소켓은 한 번 연결을 맺으면 서버·클라이언트 양쪽에서 언제든 메시지를 보낼 수 있는 풀 듀플렉스 구조라 이 요구사항에 맞았고, OCPP 자체도 웹소켓 위에서 동작하도록 정의돼 있습니다.
> 

**Q. Redis는 이 프로젝트에서 왜, 어떻게 쓰셨나요?**

> 충전기와의 통신은 방향에 따라 처리 방식이 달랐습니다. 충전기가 먼저 요청을 보내오는 경우(Heartbeat, StatusNotification 등)는 서비스가 그 자리에서 바로 응답해주면 끝나는 동기적 흐름이라 Redis가 따로 필요 없었습니다. Redis는 반대 방향 — 서비스가 충전기로 원격 명령(충전 시작/정지 같은)을 먼저 보내고 그 응답을 기다려야 하는 경우에 쓰였습니다. 서비스가 명령을 보낼 때 그 요청을 식별하는 키로 "응답 대기 중" 상태를 TTL과 함께 Redis에 먼저 저장해두고, 실제로 충전기가 응답을 보내오면 그 키를 조회해서 어떤 요청에 대한 응답인지 매칭한 뒤에만 키를 삭제하는 식으로 처리했습니다. 만약 충전기가 응답을 안 주면 TTL이 지나 키가 자동으로 사라지면서 타임아웃 처리가 되는 구조였습니다.
> 

**Q. 응답이 올 때만 키를 지운 이유는 무엇인가요? 처음부터 TTL로만 놓아두면 안 되나요?**

> 응답이 정상적으로 온 경우에는 그 응답을 받은 시점에 "이 요청은 처리 완료됐다"는 것을 모두에게 명확히 알려야 하는데, TTL만 있으면 응답이 와도 키가 만료될 때까지 남아있게 되어 타임아웃과 정상 응답을 구별할 수 없습니다. 그래서 응답이 오면 명시적으로 키를 지우고, 응답이 안 오는 경우만 TTL 만료로 자연스럽게 정리되도록 두 가지를 함께 써서, "정상 응답 처리"와 "타임아웃 안전망"을 동시에 충족했습니다.
> 

**Q. Redis에 저장한 데이터가 서버 재시작하면 날아가지 않나요? 문제 없었나요?**

> 어차피 응답 대기 상태 자체가 그 순간의 요청-응답 사이에만 의미가 있는 휘발성 데이터라서, 서버가 재시작되면서 함께 사라지는 게 오히려 자연스러웠습니다. 재시작 이후에는 어차피 그 요청 자체가 유효하지 않은 상태가 되기 때문에, 영속성을 신경 써야 하는 데이터는 아니었습니다.
> 

#### 2-2. 안전톡 v2 — 통합 인증/멀티모듈 (범용 백엔드 역량 증명)

> 아래 항목은 코드 기준으로 이미 정리해둔 `안전톡_프로젝트_실전면접QA.md` 파일 내용과 동일합니다. 이 회사는 도메인은 다르지만, **여러 클라이언트(웹/앱)가 하나의 백엔드를 공유하는 구조 설계 경험**으로 연결해서 답하면 됩니다.
> 

**Q. 여러 서비스가 하나의 백엔드 구조를 공유하도록 설계해본 경험이 있나요?**

> 네, 안전톡 v2에서 관리자 웹·관리자 앱·근로자 앱 세 클라이언트가 공통 데이터를 각자 조회하던 구조를, Core 모듈로 데이터 접근을 단일화하는 멀티모듈 구조(safety-com·safety-back·safety-web·safety-mng·safety-wrk)로 바꿨습니다. 컬럼 하나가 추가돼도 예전엔 서비스마다 찾아서 수정·재배포해야 했는데, Core 모듈 하나만 고치면 되게 만들었습니다. 인증도 마찬가지로 `UnifiedAuthFilter` 하나로 세 로그인 흐름을 통합해서, URL 패턴과 로그인 ID 형식으로 사용자 유형을 자동 추론하고 JWT 발급·갱신·기기 바인딩을 한 지점에서 관리하도록 설계했습니다.
> 

**Q. (꼬리질문) 그 구조가 통신장비/여러 채널을 다루는 회사에서는 왜 유용할까요?**

> [ ] 이 부분은 실제 지원 공고에서 "여러 디바이스/여러 클라이언트"를 다룬다는 게 확인되면 더 구체적으로 연결할 수 있습니다. 일반적으로는: 통신장비나 IoT 단말기도 종류가 여러 개면 각자 다른 프로토콜/포맷으로 서버와 통신하게 되는데, 이걸 공통 처리 지점 없이 각자 구현하면 유지보수 비용이 커집니다. Core 모듈로 공통 로직을 단일화한 경험을 "디바이스 종류가 늘어나도 확장 가능한 구조를 만들어본 경험"으로 연결해서 답할 수 있습니다.

### Java / JVM

- **JVM 메모리 구조**: Heap(객체·인스턴스 저장, GC 대상), Stack(메서드 호출마다 생기는 지역변수·호출 정보), Method Area(클래스 메타데이터·static 변수), PC Register, Native Method Stack으로 나뉩니다.
- **GC(가비지 컬렉션)**: Heap의 Young 영역(새로 생긴 객체)과 Old 영역(오래 살아남은 객체)을 나눠서 관리하는 세대별 수집이 기본 개념입니다. Young 영역은 자주, 작게 훑고(Minor GC), Old 영역은 드물게, 크게 훑습니다(Major GC). G1GC가 최근 기본 GC로, 힙을 작은 영역(Region)으로 나눠 가비지가 많은 영역부터 우선 수거합니다.
- **equals와 hashCode**: HashMap 같은 해시 기반 컬렉션에서 두 객체가 같은지 판단할 때 hashCode로 먼저 버킷을 찾고, 같은 버킷 안에서 equals로 실제 동등성을 비교합니다. equals만 재정의하고 hashCode를 재정의하지 않으면 논리적으로 같은 객체인데도 해시 기반 컬렉션에서는 다른 객체로 취급되는 문제가 생깁니다.
- **OOP 4대 특성**: 캡슐화(내부 구현 숨기기), 상속(공통 로직 재사용), 다형성(같은 메서드 호출이 실제 타입에 따라 다르게 동작), 추상화(공통 인터페이스로 구체적 구현을 감추기).

### Spring Boot

- **IoC/DI**: 객체를 개발자가 직접 `new`로 만드는 게 아니라, 스프링 컨테이너가 생성하고 필요한 곳에 주입해주는 방식입니다. 객체 간 결합도를 낮춰서, 구현체를 바꿔도 그걸 사용하는 쪽 코드는 변경할 필요가 없게 만듭니다.
- **자동 설정(Auto Configuration)**: 클래스패스에 어떤 라이브러리가 있는지를 보고(`@ConditionalOnClass` 등) 필요한 Bean을 스프링이 알아서 등록해주는 방식입니다. 예를 들어 `spring-boot-starter-web`이 있으면 내장 톰캣과 DispatcherServlet을 자동으로 설정해줍니다.
- **Filter vs Interceptor vs AOP**: 셋 다 공통 관심사를 분리하는 목적은 같지만 동작 위치가 다릅니다. Filter는 서블릿 컨테이너 레벨(스프링 컨텍스트 밖)에서 요청/응답 자체를 다루고, Interceptor는 스프링 MVC 안에서 컨트롤러 호출 전후에 개입하며, AOP는 메서드 단위로 더 세밀하게 원하는 지점(어노테이션 기반 등)에 로직을 끼워 넣을 수 있습니다.
- **계층 구조**: Controller(요청/응답 처리) → Service(비즈니스 로직) → Repository/Mapper(데이터 접근)로 역할을 나눠서, 각 계층이 자신의 책임만 갖도록 설계하는 게 기본 원칙입니다.

### MyBatis

- SQL을 직접 작성하고 그 결과를 객체에 매핑해주는 **SQL 매퍼 프레임워크**입니다. JPA 같은 ORM은 객체 중심으로 설계하면 SQL을 자동 생성해주지만, MyBatis는 SQL을 개발자가 직접 통제한다는 점이 가장 큰 차이입니다.
- 복잡한 조인이나 동적 쿼리(조건에 따라 WHERE 절이 바뀌는 경우 `<if>`, `<choose>` 태그로 처리)를 세밀하게 튜닝해야 하는 상황에 강점이 있고, 반대로 JPA의 영속성 컨텍스트 같은 자동 캐싱·변경 감지 기능은 없어서 그 부분은 직접 관리해야 합니다.
- N+1 문제는 JPA에서 자주 언급되는데, MyBatis는 SQL을 직접 쓰기 때문에 이 문제가 상대적으로 덜 발생하지만, 반대로 매핑 쿼리를 반복 호출하는 코드를 실수로 짜면 동일하게 발생할 수 있습니다.

### REST API

- 자원(Resource)을 URI로 표현하고, 그 자원에 대한 행위를 HTTP 메서드(GET 조회, POST 생성, PUT/PATCH 수정, DELETE 삭제)로 표현하는 설계 스타일입니다.
- **상태 코드**: 2xx(성공), 3xx(리다이렉션), 4xx(클라이언트 오류 — 잘못된 요청, 인증/권한 문제), 5xx(서버 오류)로 의미를 구분해서 응답합니다.
- **멱등성(Idempotency)**: 같은 요청을 여러 번 보내도 결과가 같아야 하는 성질입니다. GET/PUT/DELETE는 멱등해야 하고, POST는 호출할 때마다 새로 생성되므로 멱등하지 않습니다.

### JavaScript

- **싱글 스레드 + 이벤트 루프**: JS는 메인 스레드가 하나뿐이라 코드를 한 번에 하나씩 실행하지만, 네트워크 요청 같은 시간이 걸리는 작업은 브라우저/Node의 백그라운드에 맡기고, 끝나면 콜백을 이벤트 루프가 큐에서 꺼내 실행하는 방식으로 비동기 처리를 흉내 냅니다.
- **콜백 → Promise → async/await**: 콜백 지옥 문제를 해결하기 위해 Promise가 나왔고, async/await는 Promise를 동기 코드처럼 읽히게 만든 문법적 설탕(syntactic sugar)입니다.
- **클로저**: 함수가 자신이 선언될 때의 스코프(변수)를 기억해서, 함수 실행이 끝난 뒤에도 그 변수에 접근할 수 있는 특성입니다.

### Redis

- 디스크가 아니라 메모리에 데이터를 저장하는 **인메모리 key-value 스토어**라 읽기/쓰기 속도가 매우 빠릅니다. String, Hash, List, Set, Sorted Set 같은 다양한 자료구조를 기본 제공합니다.
- **싱글 스레드 이벤트 루프** 기반으로 명령을 순차 처리해서 별도 락 없이도 명령 단위의 원자성을 보장합니다(멀티 스레드 DB처럼 동시성 제어를 신경 쓸 필요가 적음).
- **TTL**: 키마다 만료 시간을 설정할 수 있어서, 시간이 지나면 자동으로 삭제됩니다. 실무 프로젝트처럼 "잠깐만 필요한 상태값"을 저장할 때 유용합니다.
- **영속화**: 기본은 인메모리라 휘발성이지만, RDB(스냅샷 방식)나 AOF(명령어 로그 방식)로 디스크에 백업할 수도 있습니다. 다만 순수 캐시/임시 상태 저장 용도로 쓸 땐 영속화를 꺼두는 경우도 많습니다.
- **캐시 전략**: Cache-Aside(조회 시 캐시 먼저 확인, 없으면 DB 조회 후 캐시에 채움), Write-Through(쓰기 시 캐시와 DB에 동시 반영), Write-Back(캐시에 먼저 쓰고 나중에 DB에 반영) 등이 있습니다.

### Docker

- OS 전체를 가상화하는 VM과 달리, Docker는 **커널을 공유하면서 프로세스를 격리**하는 컨테이너 방식이라 가볍고 시작이 빠릅니다.
- **이미지와 레이어**: Dockerfile의 각 명령어가 레이어로 쌓여서 이미지가 만들어지고, 컨테이너는 그 이미지를 실행한 인스턴스입니다. 레이어는 캐시되기 때문에 변경되지 않은 부분은 다시 빌드하지 않습니다.
- **격리 원리**: 리눅스의 namespace(프로세스·네트워크·파일시스템 등을 분리)와 cgroup(CPU·메모리 자원 제한)을 이용해 컨테이너 간 독립성을 보장합니다.

### CI/CD (Jenkins)

- **CI(지속적 통합)**: 코드 변경사항을 자주 병합하고, 그때마다 자동으로 빌드·테스트해서 문제를 빨리 발견하는 것.
- **CD(지속적 배포/전달)**: 빌드된 결과물을 자동으로 스테이징/운영 환경까지 배포하는 것.
- Jenkins는 Git 저장소의 push/webhook을 트리거로 받아서, 정의된 파이프라인(빌드 → 테스트 → 이미지 빌드 → 배포)을 순서대로 실행하는 자동화 도구입니다.

### Git

- 로컬에도 전체 이력을 갖고 있는 **분산 버전관리 시스템**이라, 중앙 서버 없이도 커밋/브랜치 작업이 가능합니다.
- **merge vs rebase**: merge는 두 브랜치의 이력을 그대로 합치면서 병합 커밋을 남기고, rebase는 커밋들을 다른 브랜치 위로 다시 쌓아서 이력을 한 줄로 깔끔하게 만듭니다. 공유 브랜치에는 보통 rebase를 지양합니다(이력이 꼬일 수 있어서).

### NGINX

- 클라이언트 요청을 받아 뒷단의 WAS(톰캣 등)로 넘겨주는 **리버스 프록시** 역할을 합니다.
- 여러 WAS 인스턴스에 요청을 분산하는 **로드밸런싱**, 정적 파일(이미지·JS·CSS) 직접 서빙, HTTPS 인증서 처리(SSL Termination)를 대표적으로 담당합니다.

### RDB 비교 (Oracle · PostgreSQL · MariaDB)

- 셋 다 관계형 데이터베이스로 ACID(원자성·일관성·고립성·지속성)를 보장한다는 공통점이 있습니다.
- **Oracle**: 상용 DB, PL/SQL이라는 자체 프로시저 언어, 대규모 트랜잭션 처리에 강점, 라이선스 비용이 큽니다.
- **PostgreSQL**: 오픈소스, 표준 SQL 준수도가 높고 JSON 타입·확장 기능(익스텐션)이 풍부해서 복잡한 쿼리나 다양한 데이터 타입을 다룰 때 유리합니다.
- **MariaDB**: MySQL에서 갈라져 나온 오픈소스 DB로 MySQL과 호환되며, 가볍고 웹 서비스에서 널리 쓰입니다.

### WebSocket

- 처음엔 HTTP로 연결을 시작하지만 `Upgrade` 헤더로 프로토콜을 전환해서, 이후엔 하나의 연결로 **서버·클라이언트 양쪽에서 자유롭게 메시지를 주고받는 풀 듀플렉스** 통신을 합니다.
- HTTP 폴링(계속 요청을 보내 확인)이나 롱폴링(요청을 오래 붙잡아두는 방식)과 달리, 연결을 유지한 채로 이벤트가 생길 때만 메시지를 보내기 때문에 실시간성이 필요한 서비스(채팅, IoT 상태 모니터링, 충전기 제어 등)에 적합합니다.

### OCPP (Open Charge Point Protocol)

- 전기차 충전기(Charge Point)와 중앙 관제 시스템(CSMS) 사이의 통신을 표준화한 **개방형 프로토콜**로, Open Charge Alliance에서 관리합니다.
- 웹소켓 위에서 JSON-RPC와 비슷한 구조의 메시지(Call/CallResult/CallError)를 주고받습니다.
- 주요 메시지 예시: `BootNotification`(충전기 부팅 시 등록), `Heartbeat`(생존 신호), `StatusNotification`(충전기 상태 변화), `StartTransaction`/`TransactionEvent`(충전 시작·종료, 버전에 따라 메시지명이 다름).
- 1.6과 2.0.1의 차이: 1.6이 여전히 업계에서 널리 쓰이는 구버전이고, 2.0.1은 보안(TLS, 인증서 기반) 강화, 스마트 충전(전력 분배 제어), 디바이스 관리 기능이 추가된 최신 버전입니다.

### JWT & RBAC

- **JWT 구조**: `Header.Payload.Signature` 세 부분을 점으로 이어 붙인 문자열입니다. Header에는 알고리즘 정보, Payload에는 사용자 정보 등의 claim, Signature는 서버만 아는 비밀키로 앞부분을 서명한 값입니다.
- **Stateless 인증**: 서버가 세션을 따로 저장하지 않고, 토큰 자체에 필요한 정보와 서명이 담겨 있어서 서명 검증만으로 인증이 끝납니다. 서버를 여러 대로 늘려도(수평 확장) 세션 동기화 문제가 없다는 게 장점입니다.
- **Access/Refresh 토큰 분리**: Access 토큰은 짧게(탈취돼도 피해 최소화), Refresh 토큰은 길게(재로그인 최소화) 유지해서 보안과 편의성의 균형을 맞춥니다.
- **RBAC(Role-Based Access Control)**: 사용자에게 직접 권한을 부여하는 게 아니라 역할(Role)을 부여하고, 역할마다 권한을 매핑해서 관리하는 방식입니다. 사용자 수가 많아져도 역할 단위로 권한을 관리할 수 있어 확장성이 좋습니다.
