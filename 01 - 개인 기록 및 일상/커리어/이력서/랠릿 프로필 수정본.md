# 이력서: 랠릿 프로필 수정본

## 내용

## 랠릿 프로필 수정본

> 코브원(경력 6년 이상, JPA/AWS/Docker/Jira 요구) 지원용으로 다듬은 버전입니다.
아래 표시된 부분은 그대로 복사해서 쓰셔도 되고, 본인 어투에 맞게 조금씩 손보시면 더 자연스러워질 거예요.
> 

---

### 자기소개

#### [핵심 역량]

- **실시간 프로토콜 분석 및 구현**: 담당자 퇴사로 인수받은 OCPP 1.6 웹소켓 서버를 이어받아, Redis 기반 아키텍처 위에서 실제 구현을 담당했고 이후 OCPP 2.0.1 마이그레이션 과정에서는 프로토콜 스펙 분석부터 CSMS 설계 문서 작성, 구현까지 직접 진행
- **복잡한 비즈니스 도메인 로직 처리**: 부서 간 평가 편차를 줄이기 위한 보정치 계산 및 등급 산출 로직, 벤더사 커스텀 결제 프로토콜(IC/RF 카드, 부분취소, 주차요금 연동) 설계
- **인프라 및 CI/CD 환경 구축**: Docker 기반 서버 환경 세팅, Nginx 연동, Jenkins & Gitea 기반의 모듈별/전체 선택적 배포 파이프라인 구성
- **일정 리스크 관리 및 협업 조율**: 현실과 맞지 않는 WBS 일정 및 불명확한 설계 상황에서 당장 개발 가능한 업무를 식별·재분담하여 프로젝트 지연 방지

#### [직무 경험 및 자기소개]

**1. 담당자 공백을 이어받아 프로토콜 구현을 책임진 경험**
전기차 충전 플랫폼에서 기존 담당자가 구축해 둔 OCPP 1.6 기반 웹소켓 서버를 퇴사 후 인수받았습니다. 세션·트랜잭션·메시지를 Redis 분산 캐시로 관리하고 웹소켓 서버는 DB에 직접 접근하지 않도록 API 서버와 역할을 분리하는 아키텍처 방향은 이미 잡혀 있었지만, 이를 실제로 구현하고 안정화하는 건 제 몫이었습니다. 이후 OCPP 2.0.1로 넘어가는 프로젝트에서는 상황이 달랐습니다. 설계 문서는 뼈대만 있는 상태였고, StartTransaction/StopTransaction/MeterValues 세 가지로 나뉘어 있던 메시지가 TransactionEvent 하나로 통합되는 등 메시지 구조 자체가 바뀌는 부분까지 스펙을 직접 뜯어보며 유즈케이스별 시퀀스와 CSMS 설계 문서를 채워 넣고, 그대로 구현까지 진행했습니다.

**2. 프로젝트 공백을 메우는 소통과 업무 조율**
프로젝트 진행 중 설계가 미진하거나 기존 WBS 일정에 오류가 있어 진행이 어려운 상황이 있었습니다. 이때 가만히 있기보다 현재 시점에서 실제로 진행할 수 있는 개발 범위부터 정리했습니다. 이를 단위별로 나누어 팀원들에게 공유하고 업무를 재분담함으로써 전체 일정이 밀리지 않도록 다리 역할을 했습니다.

**3. 전반적인 개발 프로세스에 대한 이해**
1인 개발부터 멀티 모듈 기반의 서비스 고도화, Docker와 Jenkins를 활용한 배포 자동화까지 서비스 전반의 과정을 직접 다뤄봤습니다. 단순히 할당된 기능 구현에 그치지 않고, 같이 일하는 동료들이 개발하기 편한 구조와 안정적인 서비스를 고민하며 일하고 있습니다.

### 프로젝트: 전기차 충전 플랫폼 구축 (소프트베리, 2023.07 ~ 2024.08)

기존 문구 유지하고, **웹소켓 서버** 담당 부분만 아래처럼 구체화하는 걸 추천드려요.

#### 웹소켓 서버 (수정본)

- 실시간 전기차 충전기와의 통신 담당
- 기존 담당자 퇴사로 OCPP 1.6 기반 서버를 인수받아 학습 후 유지보수 및 기능 개발 담당
- 충전기 세션·트랜잭션·메시지 상태를 Redis 분산 캐시로 관리하고, 웹소켓 서버가 DB에 직접 접근하지 않도록 API 서버와 역할을 분리하는 구조를 실제로 구현 (WS는 실시간 통신만, CRUD/비즈니스 로직은 API 서버가 전담)
- OCPP 1.6 기반 서버가 이미 개발된 상태에서, OCPP 2.0.1 프로토콜을 기반으로 새로운 서버 개발: 스펙을 직접 분석해 BootNotification, Authorize, StatusNotification 등 유즈케이스별 시퀀스를 정의하고 CSMS 설계 문서를 작성, 구현까지 진행
- 기존 StartTransaction/StopTransaction/MeterValues 3개 메시지로 나뉘어 있던 거래 처리를 OCPP 2.0.1의 TransactionEvent 통합 모델(txStartPoint/txStopPoint, seqNo 기반 메시지 순서 보장)에 맞게 재설계
- Security Profile Level 2(TLS + HTTP Basic Auth) 적용
- 충전기 벤더사(이지차저) 규격에 맞춘 DataTransfer 커스텀 메시지 설계 및 구현: IC/RF 카드 결제 연동, 부분취소, 주차요금 조회, 휴대폰 본인인증
- SetChargingProfile 기반 스마트 차징(충전기 그룹 전체 출력 대비 개별 충전기 출력 실시간 제어) 로직 설계
- Redis와 연동해 충전기 메시지 처리 및 API 서버와의 연계

#### 사용기술 (수정 제안)

기존: `Spring Boot, Java, MariaDB, Docker, Gitlab, Redis, REST API, HTML/CSS`
→ 필요시 `WebSocket, OCPP 1.6/2.0.1` 을 명시적으로 추가하는 것을 추천드립니다 (JD에서 프로토콜/통신 경험을 평가할 가능성이 높아서요).

### 확인해주셔야 할 부분

1. **JPA / AWS / Jira** — 코브원 공고 필수 스킬인데 현재 프로필엔 없습니다. 써보신 적 있으면 알려주세요, 관련 프로젝트 문구에 반영할게요. 없다면 면접에서 나올 가능성이 높으니 "학습 중" 정도로 언급할 준비를 해두시는 게 좋습니다.
2. **경력 6년 미달 부분** — 자기소개 맨 위(포지션/한줄소개) 쪽에 "실시간 프로토콜 구현·인프라 구축 경험" 같은 걸 짧게 강조하는 한 줄을 넣어서, 연차보다 실질 경험의 깊이를 먼저 보여주는 걸 추천드립니다. 원하시면 그 한 줄도 같이 다듬어드릴게요.
3. **표현 수위 재확인** — "설계"라는 단어가 남아있는 부분들(예: DataTransfer 벤더 커스텀 메시지, SetChargingProfile 스마트 차징)도 실제로 본인이 스펙을 정하고 구현한 게 맞는지 한 번 더 확인해주세요. 맞다면 그대로 두면 되고, 벤더사나 기획 쪽에서 이미 정해준 스펙이었다면 "설계" 대신 "구현"으로 바꾸는 게 안전합니다.
