### 제 1과목 소프트웨어 설계

#### ✏️ 객체지향 분석(Object-Oriented Analysis, OOA)

- 객체지향 분석은 사용자의 요구사항을 분석하여 요구된 문제와 관련된 모든 클래스 (객체), 이와 연관된 속성과 연산, 그들 간의 관계 등을 정의하여 모델링하는 작업
- 각 방법론은 어떤 관점에서 객체를 바라보고, 어떻게 모델링할지에 대한 생각과 표기법의 차이라고 볼 수 있음.

| Coad와 Yourdon 방법
(코드와 유어돈) | `E-R다이어그램을 사용`하여 객체의 행위를 모델링하며, 객체 식별, 구조 식별, 주제 정의, 속성과 인스턴스 연결 정의, 연산과 메시지 연결 정의 등의 과정으로 구성하는 기법 |
| --- | --- |
| Booch(부치) 방법 | `미시적(Micro)` 개발 프로세스와 `거시적(Macro)` 개발 프로세스를 모두 사용하는 분석 방법으로, 클래스와 객체들을 분석 및 식별하고 클래스의 속성과 연산을 정의함 |
| Jacobson(제이콥슨)방법 | `Use Case`를 강조하여 사용하는 분석 방법 |
| Wirfs-Brock 방법
(워프스-브록) | `분석과 설계 간의 구분이 없고`, 고객 명세서를 평가해서 설계 작업까지 연속적으로 수행하는 기법 |
| Rumbaugh(럼바우) 방법 | 분석 활동을 객체 모델, 동적 모델, 기능 모델로 `나누어 수행함` |
- 럼바우
    - 객체(Object) 모델링
        - `정보 모델링`이라고도 하며, 객체들간의 관계를 규정하여 객체들 간의 관계를 규정하여 `객체 다이어그램`으로 표시하는 것
    - 동적(Dynamic) 모델링
        - `상태 다이어그램`을 이용하여 객체들 간의 `동적인 행위`를 표현하는 모델링
    - 기능(Functional) 모델링
        - `자료 흐름도` 를 이용하여 `자료 흐름을 표현`한 모델링

#### ✏️ UML (Unified Modeling Language)

- 시스템 개발자와 고객 또는 개발자 상호 간의 의사소통이 원할하게 이루어지도록 표준화한 대표적인 객체지향 모델링 언어이다.
    - 소프트웨어 건축 설계도
- 구성 요소
    - **사물 (Things):** 설계도에 들어갈 '부품' (예: 클래스, 객체)
    - **관계 (Relationships):** 부품들을 '연결하는 방식' (예: 상속, 의존)
    - **다이어그램 (Diagrams):** 부품과 연결 방식을 조합해 만든 '실제 설계도면'

#### ✏️ UML의 주요 관계

- 부품(객체)들을 어떻게 연결할지 정하는 규칙
- 일반화(Generalization) 관계
    - 하나의 사물이 다른 사물에 비해 더 `일반적인지 구체적인지를 표현`
    - 상속 / “~는 ~의 한 종류다.” 부모-자식 관계 / 예 : `스마트폰`은 전화기의 한 종류이다.
- 의존(Dependency) 관계
    - 필요에 의해 `서로에게 영향을 주는` 짧은 `시간 동안만 연관을 유지`하는 관계를 표현
    - “필요할 때 잠깐만 가져다 쓰는 관계” / 함수의 파라미터 등 / 예 : `운전자`는 `주유소`를 잠깐 사용한다.
- 실체화(Realization) 관계
    - 사물이 `할 수 있거나 해야 하는 기능`으로 서로를 `그룹화 할 수 있는 관계`를 표현
    - “약속된 ‘기능’을 실제로 만들었다.” / 인터페이스 구현 / `갤럭시`는 `USB-C 충전`을 할 수 있다.

#### ✏️ 구조적(Structural) 다이어그램의 종류 (정적)

- `이 앱은 무엇으로 만들어졌나?` 앱의 정적인 뼈대, 부품 목록, 배치도를 보여줌
- 클래스 (Class)
    - 클래스, 속성, 연산 및 클래스 간의 관계(상속, 연관 등)을 정의
- 객체 (Object)
    - 특정 시점의 객체(클래스의 인스턴스)와 그들 사이의 관계를 보여줌
- 컴포넌트 (Component)
    - 시스템을 구성하는 물리적인 소프트웨어 컴포넌트(모듈, 라이브러리)와 그들 간의 의존 관계를 보여줌
- 배치 (Deployment)
    - 소프트웨어가 어떤 물리적인 하드웨어(서버, 장비)에 어떻게 배치되고 실행되는지를 보여줌
- 패키지 (Package)
    - 클래스나 유스케이스 등 모델의 여러 요소들을 그룹화하여 관리하는 방법을 보여줌
- 복합체 구조 (Composite Strucure)
    - 클래스나 컴포넌트의 내부 구조를 더 상세하게 보여줌

#### ✏️ 행위(Behavioral) 다이어그램 종류 (동적)

- `그래서 이 앱은 어떻게 움지이나?` 앱이 실제로 동작하는 과정, 순서를 보여줌
- 유스케이스 다이어그램 (Use Case Diagram)
    - 사용자 입장에서의 요구사항 목록
    - 사용자가 시스템으로 무엇을 할 수 있는지, 시스템의 기능과 범위를 정의
- 순차 다이어그램 (Sequence Diagram)
    - 객체들의 시간순 대화 대본
    - 하나의 기능을 처리하기 위해 여러 객체들이 어떤 순서로 메시지를 주고받는지 보여줌
- 커뮤니티케이션 다이어그램 (Communication Diagram)
    - 객체 간의 관계와 메시지 흐름을 함께 보여주는 인물 관계도
    - 과거에는 “협력 다이어그램” 이라고도 불림. 객체 간의 연결 관계(구조)와 그 관계 속제엇 오가는 메시지를 함께 보여주는 데 중점을 둠
- 상태 다이어그램 (State Diagram)
    - 하나의 객체가 특정 이벤트에 따라 자신의 상태가 어떻게 변하는지를 보여줌
- 활동 다이어그램 (Activity Diagram)
    - 업무의 처리 과정 지도
    - 어떤 기능의 시작부터 끝까지 작업이 어떤 순서와 조건으로 흘러가는지(워크플로우)를 보여줌
- 상호작용 개요 다이어그램 (Interaction Overview Diagram)
    - 여러 다이어그램을 섞어서 만든 전체 시나리오 요약본
- 타이밍 다이어그램 (Timing Diagram)
    - 시간 제약이 중요한 시스템의 상태 변화 관찰 기록

#### ✏️ 순차(Sequence) 다이어그램의 구성 요소

- 액터(Actor) : 시스템 외부의 존재
    - 시스템과 상호작용하는 사람이나 외부 시스템을 의미하며 외부 시스템을 의미
    - 예: 손님
- 객체(Object) : 시스템 내부의 존재
    - `사각형` : 상호작용에 참여하는 주체. 클래스의 인스턴스
    - 예 : 바리스타, POS 단말기, 주문서
- 생면선(Lifeline)
    - `----` : 객체 아래로 그려진 점선으로, 해당 객체가 메모리에 존재하며 활동할 수 있는 기간을 나타냄
- 실행 상자(Active Box)
    - `좁은 직사각형` : 생명선 위에 그려짐. 객체가 메시지를 받아 실제로 작업을 수행하고 있는 활성 상태(시간)을 나타냄
- 메시지(Message)
    - `→` : 객체 간에 주고받는 통신이나 요청을 화살표로 나타냄
        - `●→` : 동기 메시지
        - `→` : 비동기 메시지
        - `←-` : 동기 메시지에 대한 응답

#### ✏️ TP-Monitor

- 한마디로 “온라인 거래의 교통경찰” 이라고 생각하면 됨
- 은행이나 항공사, 대규모 쇼핑몰처럼 수많은 사용자가 동시에 접속해서 `입금`, `좌석 예약`, `결제` 같은 중요한 요청(트랜잭션)을 보낼 때, 이 요청들이 충돌 없이 안전하고 신속하게 처리되도록 관리하는 전문 미들웨어
    - 트랜잭션 관리 및 처리
        - 사용자의 요청(트랜잭션)이 중간에 끊기거나 오류가 생기지 않도록 시작부터 완료까지 모든 과정을 책임짐.
        - ACID 속성 보장: 트랜잭션의 생명과도 같은 원자성(Atomicity), 일관성(Consistency), 고립성(Ioslation), 지속성(Durability) 이 지켜지도록 감시합니다.
    - 부하 분산 (Load Balancing)
        - TP-모니터는 이 요청들을 여러 서버에 골고루 나눠주는 교통정리를 통해 특정 서버가 과부하에 걸리지 않게 합니다.
    - 동적 프로세스 관리 (Dynamic Process Management)
        - 사용자가 몰릴 때는 처리 프로세스(일꾼) 수를 늘리고, 사용자가 적을 때는 줄여서 시스템 자원을 효율적으로 사용하게 합니다. (동적 스케일링)
    - 장애 복구 (Failover & Recovery)
        - 특정 프로세스나 서버에 문제가 생기면, 진행 중이던 거래를 다른 정상적인 서버로 넘겨서 중단 없이 완료되도록 조치합니다.
- 문제에서 나온 설명
    - 트랜잭션이 올바르게 처리되고 있는지 데이터를 감시하고 제어하는 미들웨어
    - 분산 컴퓨팅 환경에서 다수의 클라이언트의 요청을 서버에 균등하게 분배하는 로드 밸런싱 기능과, 트랜잭션이 정상적으로 처리되는지 감시하고 제어하는 역할을 수행하는 미들웨어
    - 다수의 사용자가 동시에 접근하는 대규모 시스템에서 트랜잭션이 안정적이고 효율적으로 처리되도록 감시하고 제어하는 미들웨어
    

#### ✏️ 객제지향 프로그래밍 (OOP)의 핵심 원리

- **객체지향의 구성요소**
    - **클래스(Class)와 객체(Object)**
        - 클래스는 공통괸 속성과 연산(행위)을 갖는 객체의 집합
        - 클래스에 속한 각각의 객체를 인스턴스라 한다.
        - 데이터를 추상화하는 단위이다.
    - **캡슐화 (Encapsulation)**: 데이터와 기능을 하나로 묶고 외부 접근을 제한
        - 외부 모듈의 변경으로 인한 파급 효과가 적다.
        - 인터페이스가 단순화된다.
        - 재사용이 용이하다.
    - **상속 (Inheritance)**: 상위 클래스의 속성과 기능을 하위 클래스가 물려받음
    - **다형성 (Polymorphism)**: 하나의 메시지에 대해 객체마다 다른 방식으로 응답
        - 오버로딩(Overloading)
            - 메소드의 이름은 같지만 인수를 받는 자료형과 개수를 달리하여 여러 기능을 정의할 수 있음
        - 오버라이딩(Overriding)
            - 메소드의 이름은 같지만 메소드안의 실행 코드를 달리하여 자식 클래스에서 재정의해서 사용할 수 있음

#### ✏️ GoF(Gangs of Four) 디자인 패턴

- 네명의 갱단이 만든 디자인 패턴
- 생성패턴
    
    ![[02 - 학습/IT/공부기록/그 외/정보처리기사/첨부/357c3659_image.png]]
    
    - 팩토리 메소드 (Factory method)
        - `객체 생성을 서브 클래스에서 처리`하도록 분리하여 캡슐화한 패턴으로, `가상 생성자(Virtual Constructor)` 패턴이라고도 함
    - 싱글톤 (Singleton)
        - 생성된 객체를 여러 프로세스가 `동시에 참조할 수는 없음`
    - 추상화 패턴 (Abstract factory)
        - 서로 연관 ・ 의존하는 객체들의 그룹으로 생성하여 `추상적으로 표현`
    - 빌터 (Builder)
        - 작게 분리된 인스턴스를 건축하듯이 `조합하여 객체를 생성`
    - 프로토타입 (Prototype)
        - `원본 객체를 복제`하는 방법으로 객체를 생성
