#### 구현, 테스트 (2과목)

### 요구사항 분석

- 도
    - 도출 (Elicitation)
    - 도출 기법
        - 사용자의 머릿속에 있는걸 다 끄집어 내는 것
- 분
    - 분석 (Analysis)
    - 도출한걸 잘 정리해서 할 수 있는지 없는지 판단하고 고객과 협의
        - 요구사항 분류
        - 개념 모델링
        - 기술 구조 설계 및 요구사항 할당
        - 요구사항 협상
- 명
    - 명세 (Specification)
    - 협의된 내용을 문서화, 명세
        - 시스템 정의서
        - 시스템 요구사항 명세서
        - 소프트웨어 요구사항 명세서
- 확
    - 확인 (Validation)
    - 고객과 만나서 확인 후 사인하는 것
        - 검토
        - 프로토타이핑
        - 모델 검증
        - 인수테스트
- 소프트웨어 설계에서 요구사항 분석에 대한 설명으로 틀린 것은?
    1. 소프트웨어가 무엇을 해야하는가를 추적하여 요구사항 명세를 작성하는 작업이다.
    2. 사용자의 요구를 추출하여 목표를 정하고 어떤 방식으로 해결할 것인지 결정하는 단계이다.
    3. 소프트웨어 시스템이 사용되는 동안 발견되는 오류를 정리하는 단계이다.
    4. 소프트웨어 개발의 출발점이면서 실질적인 첫 번째 단계이다.

### 객체지향특징

- 캡슐화 (Encapsulation)
- 정보은닉 (Information Hiding)
- 상속 (Inheritance:인허리텐스)
    - 상위 클래스의 메소드와 속성을 하위 클래스가 물려받는 것을 의미
- 다형성 (Polymorphism)
    - 오버로딩 : 동일 메서드에 인자만 다름
    - 오버라이딩 : 상속관계에서만 존재 → 물려받은 메서드를 재정의하는 것
- 추상화 (Abstraction)

- 클래스 (Class)

- 메소드 (Method)
    - 행위
- 메세지 (Message)

        - 단순성

- **스크럼** (SCRUM)
    - 스프린트 : 짧은 단위(보름 ~ 한달)
        - 짧은 단위내에 실행이 가능한 소프트웨어가 만들어져야함

- 크리스탈
- 린 (Lean)

#### UML 다이어그램

- 정적 (구조) 다이어그램
    - 클래스 다이어그램 : 클래스의 속성, 메서드로 구성된 정적 다이어그램
    - 컴포넌트 다이어그램 : 컴포넌트들 간의 관계
    - 객체 다이어그램 : 인스턴스
    - 컴포지트 구조 다이어그램 : 아키텍처 다이어그램
    - 배치 다이어그램 : 컴포넌트들의 물리적 구성
    - 패키지 다이어그램 : 관련있는 모델링 요소들을 그룹화
- 동적 (행위) 다이어그램
    - 활동 다이어그램 : 활동의 흐름
    - 유스케이스 다이어그램 : 사용자 관점에서 바라본 시스템을 표현
        - 관계 설명 꼭 확인
    - 상태 다이어그램 : 객체의 상태 변화
    - 시퀀스 다이어그램: 시간적 흐름에 따른 메시지 교환
    - 커뮤니티케이션 다이어그램 : 객체들이 주고 받는 메시지 표현
    - 인터렉션 오버뷰 다이어그램 : 활동 다이어그램 + 시퀀스 다이어그램
    - 타이밍 다이어그램 : 시간의 흐름에 따른 상태 변화를 표현
    - 순차 다이어그램

#### LOC 기법  (비용산정)

- 1과목에 비용산정이 없는데 5과목 문제가 1과목에 나온 이유는 5과목에 과락만들려고
- 총 라인수 36000라인, 6명의 개발자 , 한명이 월 300라인
    - 6 * 300 = 1800라인
    - 36000 / 1800 = 20 개월

#### 객체지향 설계원칙(클래스 설계원칙)

SOLID

- 단일 책임원칙 (Single responsibility principle)
    - 하나의 클래스는 하나의 일만 수행해야한다.
- 개방-폐쇄의 원칙 (Open/closed principle)
    - 클래스는 확장에 대해 열려 있어야 하며 변경에 대해 닫혀 있어야 한다.
- 리스코프 치환 원칙 (Liskov Substitution Principle)
    - 자식클래스는 언제든 부모클래스를 대체할 수 있어야한다.
- 인터페이스 분리 원칙 (Interface segregation principle)
    - 쓸데없는 인터페이스 만들지 말아라
- 의존관계 역전의 원칙 (Dependency inversion principle)
    - 자주 변경되는거에 의존하지 말아라

#### 아키텍처 설계과정

- 아키텍처 → 구조
    - 시스템 아키텍처 : 시스템의 전체적인 구성도
    - 소프트웨어 아키텍처 : 소프트웨어 전체적인 구성도
        - 설계 목표 설정 → 시스템 타입 결정 → 스타일 적용 및 커스터마이즈 → 서브시스템의 기능, 인터페이스 동작 작성 → 아키텍처 설계 검토

#### 사용자 인터페이스 설계

- 심미성 - 예쁜거를 말하는거임
- 사용성을 심미성보다 우선하여 설계해야 한다.
- 효율성을 높이게 설계해야 한다.
- 발생하는 오류를 쉽게 수정할 수 있어야 한다.
- 사용자에게 피드백을 제공해야 한다.

#### UI 설계원칙 (중요)

- 직관성
    - 누구나 쉽게 이해하고 사용할 수 있어야 함
- 유효성
    - 사용자의 목적을 정확하게 달성하여야 함
- 학습성
    - 누구나 쉽게 배우고 익힐 수 있어야 함
- 유연성
    - 사용자의 요구사항을 최대한 수용하며, 오류를 최소화하여야 함

#### 럼바우 (Rumbaugh) 객체지향 분석 기법 (필기,실기 중요)

- 객체지향 분석기법의 하나로 객체모형, 동적 모형, 기능 모형의 3개 모형을 생성하는 방법
- 객체 모델링 (Object Modeling) - 구조
    - 객체 다이어그램
- 동적 모델링 (Dynamic Modeling) - 구조의 상태
    - 상태 다이어그램
- 기능 모델링 (Functional Modeling) - 데이터가 어떻게 흘러가는지
    - 자료흐름도 (DFD)

#### FEP (틀리라고 낸거라서 통으로 외우는게 좋음)

- 입력되는 데이터를 컴퓨터의 프로세서가 처리하기 전에 미리 처리하여 프로세서가 처리하는 시간을 줄여주는 프로그램이나 하드웨어를 말하는 것

#### 클린 코드 작성 원칙

- 가독성
    - 이해하기 쉬운 용어를 사용한다.
- 단순성
    - 한 번에 한 가지 처리만 수행한다.
- 의존성
    - 코드의 변경이 다른 부분에 영향이 없게 작성한다.
- 중복성
    - 중복된 코드를 제거하고, 공통된 코드를 사용한다.
- 추상화
    - 상세 내용은 하위 클래스에서 구현한다.

#### 정형 기술 검토 (FTR)

- 제작자가 아닌 제품의 검토에만 집중한다
- 문제 영역을 명확히 표현한다
- 제기된 모든 문제를 바로 해결하고자 하지 말 것
- 검토자들은 사전에 작성한 메모들을 공유한다
- 논쟁이나 반박을 제한한다
- 의제를 정하고 그 범위를 유지한다
- 참가자의 수를 제한하고, 사전 준비를 철저히 하도록 가용한다
- 자원과 시간 일정을 할당한다
- 모든 검토자에게 의미있는 교육을 행한다
- 검토의 과정과 결과를 재검토한다

#### 소프트웨어 삼학

- 재공학
    - 유지운영하자
- 역공학 (Reverse Engineering)
    - 순공학 : 계획 → 분석 → 설계 → 테스트 .. 순차적으로 가는 것
    - 역공학은 소스코드만으로 문서를 추출하는 것
- 재사용
    - 만들어져있던거 재사용
- 소프트웨어 재공학의 주요 활동 중 기존 소프트웨어 시스템을 새로운 기술 또는 하드웨어 환경에서 사용할 수 있도록 변환하는 작업
    - Migration 마이그레이션

#### 소프트웨어 패키징

- 소스코드 묶고, 설치메뉴얼 사용자메뉴얼을 묶는 것. → 릴리즈 노트
- 사용자 중심으로 진행
- 신규 및 변경 개발소스를 식별하고, 이를 모듈화하여 상용제품으로 패키징한다.
- 고객의 편의성을 위해 매뉴얼 및 버전관리를 지속적으로 한다.
- 범용 환경에서 사용이 가능하도록 일반적인 배포 형태로 패키징이 진행된다

#### 소프트웨어 패키징 도구 활용 시 고려 사항

- 반드시 암호화/보안을 고려한다.
- 추가로 다양한 이기종 연동을 고려한다. (범용 환경이랑 동일한 내용)
- 사용자 편의성을 위한 복잡성 및 비효율성 문제를 고려한다.
- 애플리케이션의 종류에 적합한 암호화 알고리즘을 적용한다.
- 지속적인 배포를 고려한다.

    - 몇 가지 필드를 쉼표(,)로 구분한 텍스트 데이터 및 텍스트 파일

    - XML, C, 파이썬, 펄, RFC2822에서 정의된 e-mail 양식에 개념을 얻어 만들어진 ‘사람이 쉽게 읽을 수 있는’ 데이터 직렬화 양식

#### 정렬

- 퀵 정렬
    - 피벗
- n²
    - 4*4 = 16
    - 16번을 돌려봐야지 정렬이 되는 것을 말함
    - 선택정렬, 삽입정렬, 버블정렬
- nlog2n
    - 퀵정렬, 힙정렬, 병합정렬 → 퀵힙병 → 희귀병
    - 성능이 좀 더 좋은 알고리즘
- 위 두 예시를 가진 계산법
    - 데이터가 8인 경우
    - n² : 8*8 = 64번 돌려야 정렬
    - 8*log28 → 8은 2³ → log옆에 2제거, 2³ 에 2제거 → 8*3 =24

#### ISO/IEC 9126

- 기 능성 : 사용자가 요구하는 기능 그대로 동작해야한다.
- 신 뢰성 : 오류가 없어야한다.
- 사 용성 : 사용하기 편리해야하고 배우기 좋아야한다.
- 효 율성 : 자원들(CPU,메모리)을 효율적으로 사용해야한다.
- 유 지보수성 : 오류가 있을 때 바로 고쳐준다.
- 이 식성 : A시스템에서 B시스템으로 이전할 수 있어야한다.

#### 소스코드 품질 분석 → 리팩토링

        - 팀 회의라고 보면 됨
- 인스펙션 (Inspection)
    - 공식적 검사회의
    - 작업자 외 다른 전문가가 검사하는 가장 공식적인 리뷰 기법

    1. 개발 정보시스템의 특성 → Java로 되어있으면 아파치로

    3. 컴파일러의 가용성
    4. 컴파일러의 독창성

    2. 이해하기 쉽고 코드 변환이 용이하다.
    3. 화살표나 GOTO를 사용하여 이해하기 쉽다.
    4. 이해하기 쉽고 코드 변환이 용이하다.
